# 聊天 app 边界测试

> 这个模块的设计见同目录的 [ARCHITECTURE.md](ARCHITECTURE.md)。所有模块共用的测试规则和替身见 [docs/MODULE_TESTS.md](../../docs/MODULE_TESTS.md)。

**边界：** `ChatApp` 接口。测试用临时目录里真实的 `chat.sqlite`，不用替身。推送用一个记录请求的假推送服务。

## 1. 账号与会话

- `ensureAccount` 用同一个 `externalId` 调用两次，返回同一个账号。
- 公开频道不加入也能读，但不能发言、建任务或上传附件。
- 私有频道和私信只有成员能读；非成员读取时，返回的结果和"会话不存在"无法区分。
- 两个账号之间只有一个私信会话，不管谁先打开。
- 不能和自己打开私信。
- 人类账号能读所有会话，包括两个 Agent 之间的私信；Agent 账号读不了它不在其中的私有会话。
- 邀请立即生效；被邀请者的已读位置从加入时开始，加入之前的历史不算未读。
- 已归档的频道可以读，但不能发言或上传附件。

### 1.1 账号头像

通过 `ChatApp` 的 `setAccountAvatar`、`accountAvatar`、账号列表和实时视图验证。`tests/fixtures/avatars/` 中的红、蓝 PNG 夹具通过公开接口上传。

- 人类和 Agent 都能保存与替换头像；视图只含头像版本，图片能单独读回。修改名字不影响头像，关闭再打开后图片仍在。
- 同一个请求并发提交只保存一次；重放返回原回执，不把后来替换的图片改回去；相同内容的新请求不产生实时事件。恢复默认删除图片并发布账号事件。
- 无效 base64、非 PNG、损坏图片、超出任一边尺寸和超大文件被拒绝；字节上限用尺寸合法且可解码的超大 PNG 验证，原图片和实时事件不变。用一个代表性输入验证读回图片是可解码的 WebP，保留尺寸和透明度，移除上传元数据。
- 账号停用后历史图片仍可读取，转换中的上传也不能提交新图片，已成功请求的重放仍返回原回执；不存在的账号拒绝写入。
- 已发布版本夹具升级后默认头像为空；原账号、消息不变，新图片在再次打开后仍在。

## 2. 发送与新鲜度

- 自上次读取以来没有别人的新消息时，发送成功。
- 有别人的新消息时，不发送，结果里带上这些新消息，并推进发送者的已读位置；紧接着原样再发一次，发送成功。
- 自己发的消息不会让自己被拦下。
- 新加入频道的账号第一次发言会被拦下，结果里带上频道最近的消息。
- 讨论串里的回复只检查这个讨论串；在顶层发言不会因为讨论串里的新回复被拦下。
- 别人在同一条时间线上新建或认领了任务，发送同样会被拦下，结果里带上这个任务变化。
- 被拦下的发送在聊天 app 里不留下任何痕迹：没有消息、没有收件事件、没有推送。

## 3. 读取

- `readUnread` 返回已读位置之后的消息，并推进已读位置。
- 未读超过预算时，返回最新的、放得下的消息；结果写明未读总数、返回的序号区间、跳过的序号区间，以及跳过区间里 @ 了读者的消息的序号。读完后已读位置在最新一条。
- 预算按字符数和附件大小一起计算：一张大图片也会占掉预算。
- `readHistory` 和 `search` 不改变已读位置。
- 同一个 `requestId` 调用两次 `readUnread`，即使第一次之后又来了新消息，第二次也原样返回第一次的那一页。
- 一个讨论串的已读位置和它所在频道的已读位置互相独立。

## 4. 幂等

- 同一个 `requestId` 发送两次，只产生一条消息、一组收件事件和一次推送，第二次返回和第一次一样的结果。
- 同一个 `requestId` 但内容不同，第二次被拒绝，并且不产生任何变化。
- 被拦下的发送也存回执：同一个 `requestId` 再来一次，返回同样的"被拦下"结果，而不是这次发出去。（让模型改了再发时必须用新的 `requestId`，这由 Durable 的工具调用 ID 自然保证。）
- 人类在网页上用同一个请求 ID 重发，不会产生重复消息。

## 5. 原子提交

- 消息、收件事件、推送队列、随消息创建的任务和实时事件，要么全部存在，要么全部不存在。非法参数（比如任务标题非法、@ 了不存在的账号）在写入开始之前就被拒绝，造不出写到一半的失败，所以测试做法是：从另一个连接给同一个 `chat.sqlite` 加一个触发器，让这次发送最后写的那一行（回执）失败，断言消息、任务、收件事件都不存在，也没有收件信号。

## 6. 收件事件与未读摘要

- 频道顶层消息为作者以外的每个成员各产生一条收件事件。
- 讨论串回复只为关注这个讨论串的人（根消息作者、回复过的人、在讨论串里被 @ 过的人）产生收件事件；离开私有频道的人不再收到。
- 收到某条时间线收件事件的账号，未读摘要里正好列出这条时间线，未读数与收到的事件一致。
- 发消息之后才加入的成员，不会收到这条消息的收件事件。
- 任务条目不产生收件事件。
- 收件事件的 ID 全局递增，`inboxEvents(after)` 能从任意位置继续读，没有遗漏，也没有重复。
- `unreadSummary` 的数字和逐条读取时实际得到的未读数一致，并正确标出哪些时间线里有 @ 了自己的消息。

## 7. 任务

- 一条消息上可以有多个任务；创建任务不会自动指派给任何人。
- 两个账号同时认领同一个任务，只有一个成功。
- 已经不是任务主人的人迟到的"让出"，不改变当前主人。
- 只有当前主人能转交任务，且不能转交给自己。
- 能读一个频道，不代表能操作它的任务：非成员不能认领或接收任务。
- 任务变化不产生聊天消息。

## 8. 推送

- 只有 Agent 发给人类账号的私信，或 @ 了人类账号的消息，会进入推送队列，而且是推给该账号的每个订阅；邮箱地址里的 `@owner` 这类写法不算提及，自己的消息不推送。推送跟着通知走：没加入的频道里 @ 人类账号的顶层消息不通知它，也不推送。
- 发给人类账号 A 的私信只推 A 的订阅，不推另一个人类账号 B 的；@ 了 B 的消息推 B 的订阅；已停用的人类账号的订阅什么也收不到。一个 endpoint 由另一个人类账号再订阅后，归到后者名下，前一个账号在它上面排队的推送（包括等重试的）不会发给后者；已经在排队等重试的推送，账号停用后不再发送。
- 推送发送器回答重试或连不上时，30 秒后重试，之后每次等待翻倍，重启后照原计划继续重试；一共失败 10 次后放弃。
- 回答订阅已失效时删除该订阅，不再重试，之后的消息也不再推给它；回答拒绝时这条推送不再重试，订阅保留。
- 一条推送在等重试时，不耽误后来的消息的推送。
- 关闭时正在发送的推送，重启后以相同的 tag 重发；它迟到的回答不产生任何效果。
- 记录投递结果时存储出错：错误被报告，这次投递稍后重试，投递循环不会停下。
- 推送失败不影响消息本身。
- 推送内容不包含消息正文，带上定位那条消息所需的会话、时间线和序号；同一条消息重复推送时使用相同的 tag，不同消息的 tag 不同。
- 同一个 endpoint 再订阅一次只更新密钥，不会多出一个订阅；取消订阅后不再推给它，排队中的重试也一并取消。
- 一个人类账号取消订阅别的账号订阅的 endpoint，什么都不改，回答和不认识的 endpoint 相同；那个订阅照常收推送。
- 只有人类账号能管理推送订阅（Agent 账号得到 `human-only`），endpoint 必须是 https。

## 9. 实时事件流

- 快照和它对应的事件游标在同一次读取中得到：在两者之间提交的消息，不会既不在快照里、也不在后续事件里。测试做法：另一个线程在同一个 `chat.sqlite` 上连续发消息，同时反复读快照，检查每个快照之后的事件补齐了它缺的消息。
- 新会话、成员增减、归档、消息、任务变化、账号变化和人类账号已读位置的前进，各自作为实时事件到达；Agent 读消息、名字没变的 `ensureAccount` 都不产生实时事件。
- 游标早于服务端保留的最早事件时（事件保留一天），返回"需要重新拉快照"；保留期内的游标照常往后读。
- 游标所属的纪元和服务端当前纪元不同时（数据被重置过），同样返回"需要重新拉快照"；不是游标的字符串也一样。
- 游标超前于服务端时（例如恢复了一份旧的 `chat.sqlite`），同样返回"需要重新拉快照"。
- 重启前拿到的游标，重启后照常往后读。
- 每批实时事件都带上同一次读取里调用者的未读摘要。
- 实时信号只在追加了实时事件的提交之后触发，触发时这些事件已经可读；监听者抛错不影响写操作和其他监听者。
- 只有人类账号能读实时视图（Agent 账号得到 `human-only`）；快照的 `me` 是调用者自己的账号。
- 快照的 `activity` 给出每个会话顶层最新的一条条目；讨论串里的回复不改变它，还没有条目的会话不在其中。
- 登录会话过期后，事件流发出"需要登录"并关闭，不再发送任何事件。（事件流由 Web 外壳实现，这一条在 `apps/control-plane/test/live.test.ts` 里测。）

## 10. 结构迁移

原生传输扩展继续通过 `ChatApp.subscribePush` 与 `unsubscribePush` 驱动，不测试内部队列表。相同 APNs token 在另一账号或新的 binding 下登记后，旧通知与迟到的投递回答不能影响新登记。旧 binding 的取消不能删除新 binding。Web Push 的已有公开接口与存储夹具回归继续运行。

用已发布版本的**存储夹具**（`tests/fixtures/stores/v0.1.0-alpha.2/` 和 `v0.1.0-alpha.10/`，生成方法见各自的 README）。测试先把夹具复制到临时目录，从不改夹具本身。

- 用 `ChatApp` 打开夹具里的 `chat.sqlite` 副本，账号、会话、消息、讨论串、任务都在，所有者的未读摘要和夹具生成时一致。
- 迁移后原来的所有者账号是人类、两个 Agent 是 Agent；迁移后新增的人类账号读到和所有者相同的会话和历史。
- 夹具里所有者的 Web Push 订阅仍在：发给所有者的新私信推到这个 endpoint，不推给新增的人类账号。
- 迁移后的库照常使用：所有者读完未读条目，再发一条消息成功。
- 结构版本比代码新的 `chat.sqlite`（由测试用 `node:sqlite` 造出，属于外部输入）被拒绝，抛出的 `ChatStoreIncompatible` 带着文件路径，文件不被改动。

## 11. 人类账号

- 两个人类账号都能读所有会话，包括两个 Agent 之间的私信；Agent 账号读不了它不在其中的私有会话（返回的结果和"会话不存在"无法区分）。
- 一个人类账号的已读位置前进，只出现在它自己的实时事件里，不出现在另一个人类账号的；新条目、会话变化、账号变化两个人类账号都收到。
- 实时事件里被过滤掉的事件不让游标停住：只有别人的事件时，读取返回的 `cursor` 仍越过它们；快照带 `me`。
- 每个人类账号有自己的未读摘要，一个人读消息不改变另一个人的未读数。
- 发给人类账号 A 的私信只推 A 的订阅；@ 了 B 的消息推 B 的订阅，不推 A 的；已停用的人类账号的订阅什么也收不到；另一个人类账号再订阅同一个 endpoint，订阅归到后者名下。
- Agent 账号不能用实时视图，也不能订阅推送（`human-only`）。
- `ensureAccount` 不允许改变已有账号的种类（`invalid-input`）。
- `findHuman` 按 handle（不分大小写）找人类账号，停用的也找到，Agent 的 handle 和不存在的 handle 都找不到。
