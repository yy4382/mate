# Mate 模块边界测试说明

> 配套文档：[ARCHITECTURE.md](ARCHITECTURE.md)。读这份之前请先读架构文档的第 2、4 节。

## 1. 规则

1. **只测模块边界，不写单元测试。** 测试只通过模块对外的接口（架构文档第 4 节列出的方法、HTTP 路由、WebSocket 协议、CLI 命令）驱动模块，只断言从接口上能观察到的结果。不 import 模块内部文件，不检查内部表结构，不 mock 模块内部的函数。
2. **边界外的依赖用替身。** 替身只能替换另一个模块或外部系统，不能替换被测模块自己的一部分。第 2 节列出允许的替身。
3. **失败和恢复路径与正常路径同等重要。** 每个模块都要覆盖：调用方重复调用、中途崩溃后重启、依赖方不可用。只跑通正常路径不算验收。
4. **测试要能说明"为什么"。** 每个测试名用一句完整的话描述行为，例如"同一个 requestId 重复发送只产生一条消息"。
5. **模型不是被测对象。** 模型由脚本扮演，测的是"模型做出某个选择之后，系统能否正确兑现"。不测模型会不会做出那个选择。
6. **假实现和真实集成要分得清。** 用了替身的测试不能叫"集成测试"。真实提供商和真实 VPS 的检查不在本文范围内。

## 2. 替身与测试工具

这些工具本身也是要写的代码，并且优先实现，因为后面每个模块的测试都依赖它们。

| 名称 | 替代什么 | 能力 | 用于 |
|---|---|---|---|
| **脚本化提供商** | 模型提供商 | 本地 HTTP 服务，按真实提供商协议（先做 OpenAI Responses）返回 SSE。脚本由命名步骤组成，每步收到真实请求体和请求带的 API key，可以回答文本（也可以是在输出上限处被截断的文本）、发起工具调用、只发一半、卡住不回、返回 4xx/5xx（和 OpenAI 一样，5xx 是会被重试的服务端错误，4xx 不是）。按会话 ID 区分不同 Agent 的请求；不带会话 ID 的请求（压缩的摘要请求）不属于任何会话，按请求体逐个认领。`assertComplete()` 检查：没有用完的步骤、没有多余的请求、没有未声明的取消，任何一项不满足都报错，并写明是哪个 Agent 的哪一步 | runtime、Manager、管理模块、系统场景 |
| **可控时钟** | 系统时间 | 测试推进时间，触发定时器 | runtime（提醒）、聊天 app（推送退避）、网关（心跳） |
| **故障存储适配器** | Durable 的 SQLite 适配器 | 包装真实的 SQLite 适配器，可以在第 N 次提交之前或之后让提交失败或挂起，用来模拟"写到一半崩溃" | runtime、连接器 |
| **假 node** | node 进程 | 实现 node 的 WebSocket 协议，测试控制工具调用：返回结果、流式输出、挂起、断开连接 | 网关、runtime、Manager |
| **假网关** | 控制面的 node 网关 | 实现网关一侧的协议：配对、认证、发送工具调用、断开连接 | node |
| **假聊天 app** | 聊天 app | 只在 runtime 的测试里使用，实现 `ChatApp` 接口里聊天工具用到的那部分，并记录收到的调用 | runtime（只测工具转发时） |
| **网络代理** | node 与控制面之间的 TCP 连接 | 三种模式：转发、黑洞（吞掉数据但不关闭连接）、断开 | 网关与 node 的心跳和重连 |
| **假 systemd** | `systemctl`、`journalctl`、用户管理器 | 放在 PATH 上的假命令，按测试设定的状态回答，并记录被调用的参数 | node CLI |
| **进程夹具** | 无 | 以真实子进程启动控制面或 node，能 SIGKILL 后在同一个数据目录上重启 | 系统场景 |

**崩溃怎么模拟：** 优先用故障存储适配器，在进程内让提交在指定点失败或挂起，然后关闭并重新打开模块，比如重新调用 `AgentRuntime.open`。少数必须验证"进程真的死了"的场景用进程夹具 SIGKILL。不使用 eval 字符串或全局变量注入故障。

## 3. 聊天 app

**边界：** `ChatApp` 接口。测试用临时目录里真实的 `chat.sqlite`，不用替身。推送用一个记录请求的假推送服务。

### 3.1 账号与会话

- `ensureAccount` 用同一个 `externalId` 调用两次，返回同一个账号。
- 公开频道不加入也能读，但不能发言、建任务或上传附件。
- 私有频道和私信只有成员能读；非成员读取时，返回的结果和"会话不存在"无法区分。
- 两个账号之间只有一个私信会话，不管谁先打开。
- 不能和自己打开私信。
- 人类账号能读所有会话，包括两个 Agent 之间的私信；Agent 账号读不了它不在其中的私有会话。
- 邀请立即生效；被邀请者的已读位置从加入时开始，加入之前的历史不算未读。
- 已归档的频道可以读，但不能发言或上传附件。

### 3.2 发送与新鲜度

- 自上次读取以来没有别人的新消息时，发送成功。
- 有别人的新消息时，不发送，结果里带上这些新消息，并推进发送者的已读位置；紧接着原样再发一次，发送成功。
- 自己发的消息不会让自己被拦下。
- 新加入频道的账号第一次发言会被拦下，结果里带上频道最近的消息。
- 讨论串里的回复只检查这个讨论串；在顶层发言不会因为讨论串里的新回复被拦下。
- 别人在同一条时间线上新建或认领了任务，发送同样会被拦下，结果里带上这个任务变化。
- 被拦下的发送在聊天 app 里不留下任何痕迹：没有消息、没有收件事件、没有推送。

### 3.3 读取

- `readUnread` 返回已读位置之后的消息，并推进已读位置。
- 未读超过预算时，返回最新的、放得下的消息；结果写明未读总数、返回的序号区间、跳过的序号区间，以及跳过区间里 @ 了读者的消息的序号。读完后已读位置在最新一条。
- 预算按字符数和附件大小一起计算：一张大图片也会占掉预算。
- `readHistory` 和 `search` 不改变已读位置。
- 同一个 `requestId` 调用两次 `readUnread`，即使第一次之后又来了新消息，第二次也原样返回第一次的那一页。
- 一个讨论串的已读位置和它所在频道的已读位置互相独立。

### 3.4 幂等

- 同一个 `requestId` 发送两次，只产生一条消息、一组收件事件和一次推送，第二次返回和第一次一样的结果。
- 同一个 `requestId` 但内容不同，第二次被拒绝，并且不产生任何变化。
- 被拦下的发送也存回执：同一个 `requestId` 再来一次，返回同样的"被拦下"结果，而不是这次发出去。（让模型改了再发时必须用新的 `requestId`，这由 Durable 的工具调用 ID 自然保证。）
- 人类在网页上用同一个请求 ID 重发，不会产生重复消息。

### 3.5 原子提交

- 消息、收件事件、推送队列、随消息创建的任务和实时事件，要么全部存在，要么全部不存在。非法参数（比如任务标题非法、@ 了不存在的账号）在写入开始之前就被拒绝，造不出写到一半的失败，所以测试做法是：从另一个连接给同一个 `chat.sqlite` 加一个触发器，让这次发送最后写的那一行（回执）失败，断言消息、任务、收件事件都不存在，也没有收件信号。

### 3.6 收件事件与未读摘要

- 频道顶层消息为作者以外的每个成员各产生一条收件事件。
- 讨论串回复只为关注这个讨论串的人（根消息作者、回复过的人、在讨论串里被 @ 过的人）产生收件事件；离开私有频道的人不再收到。
- 收到某条时间线收件事件的账号，未读摘要里正好列出这条时间线，未读数与收到的事件一致。
- 发消息之后才加入的成员，不会收到这条消息的收件事件。
- 任务条目不产生收件事件。
- 收件事件的 ID 全局递增，`inboxEvents(after)` 能从任意位置继续读，没有遗漏，也没有重复。
- `unreadSummary` 的数字和逐条读取时实际得到的未读数一致，并正确标出哪些时间线里有 @ 了自己的消息。

### 3.7 任务

- 一条消息上可以有多个任务；创建任务不会自动指派给任何人。
- 两个账号同时认领同一个任务，只有一个成功。
- 已经不是任务主人的人迟到的"让出"，不改变当前主人。
- 只有当前主人能转交任务，且不能转交给自己。
- 能读一个频道，不代表能操作它的任务：非成员不能认领或接收任务。
- 任务变化不产生聊天消息。

### 3.8 推送

- 只有 Agent 发给人类账号的私信，或 @ 了人类账号的消息，会进入推送队列，而且是推给该账号的每个订阅；邮箱地址里的 `@owner` 这类写法不算提及，自己的消息不推送。推送跟着通知走：没加入的频道里 @ 人类账号的顶层消息不通知它，也不推送。
- 发给人类账号 A 的私信只推 A 的订阅，不推另一个人类账号 B 的；@ 了 B 的消息推 B 的订阅；已停用的人类账号的订阅什么也收不到。一个 endpoint 由另一个人类账号再订阅后，归到后者名下，前一个账号在它上面排队的推送（包括等重试的）不会发给后者；已经在排队等重试的推送，账号停用后不再发送。
- 推送服务返回暂时性失败时（连不上、408、429、5xx），30 秒后重试，之后每次等待翻倍，重启后照原计划继续重试；一共失败 10 次后放弃。
- 返回 404/410 时删除该订阅，不再重试，之后的消息也不再推给它；返回其他状态码时这条推送不再重试，订阅保留。
- 一条推送在等重试时，不耽误后来的消息的推送。
- 关闭时正在发送的推送，重启后以相同的 tag 重发；它迟到的回答不产生任何效果。
- 记录投递结果时存储出错：错误被报告，这次投递稍后重试，投递循环不会停下。
- 推送失败不影响消息本身。
- 推送内容不包含消息正文，带上定位那条消息所需的会话、时间线和序号；同一条消息重复推送时使用相同的 tag，不同消息的 tag 不同。
- 同一个 endpoint 再订阅一次只更新密钥，不会多出一个订阅；取消订阅后不再推给它，排队中的重试也一并取消。
- 一个人类账号取消订阅别的账号订阅的 endpoint，什么都不改，回答和不认识的 endpoint 相同；那个订阅照常收推送。
- 只有人类账号能管理推送订阅（Agent 账号得到 `human-only`），endpoint 必须是 https。

### 3.9 实时事件流

- 快照和它对应的事件游标在同一次读取中得到：在两者之间提交的消息，不会既不在快照里、也不在后续事件里。测试做法：另一个线程在同一个 `chat.sqlite` 上连续发消息，同时反复读快照，检查每个快照之后的事件补齐了它缺的消息。
- 新会话、成员增减、归档、消息、任务变化、账号变化和人类账号已读位置的前进，各自作为实时事件到达；Agent 读消息、名字没变的 `ensureAccount` 都不产生实时事件。
- 游标早于服务端保留的最早事件时（事件保留一天），返回"需要重新拉快照"；保留期内的游标照常往后读。
- 游标所属的纪元和服务端当前纪元不同时（数据被重置过），同样返回"需要重新拉快照"；不是游标的字符串也一样。
- 游标超前于服务端时（例如恢复了一份旧的 `chat.sqlite`），同样返回"需要重新拉快照"。
- 重启前拿到的游标，重启后照常往后读。
- 每批实时事件都带上同一次读取里调用者的未读摘要。
- 实时信号只在追加了实时事件的提交之后触发，触发时这些事件已经可读；监听者抛错不影响写操作和其他监听者。
- 只有人类账号能读实时视图（Agent 账号得到 `human-only`）；快照的 `me` 是调用者自己的账号。
- 登录会话过期后，事件流发出"需要登录"并关闭，不再发送任何事件。（事件流由 Web 外壳实现，这一条在 `apps/control-plane/test/live.test.ts` 里测。）

### 3.10 结构迁移

用已发布版本的**存储夹具**（`tests/fixtures/stores/v0.1.0-alpha.2/`，生成方法见它的 README）。测试先把夹具复制到临时目录，从不改夹具本身。

- 用 `ChatApp` 打开夹具里的 `chat.sqlite` 副本，账号、会话、消息、讨论串、任务都在，所有者的未读摘要和夹具生成时一致。
- 迁移后原来的所有者账号是人类、两个 Agent 是 Agent；迁移后新增的人类账号读到和所有者相同的会话和历史。
- 夹具里所有者的 Web Push 订阅仍在：发给所有者的新私信推到这个 endpoint，不推给新增的人类账号。
- 迁移后的库照常使用：所有者读完未读条目，再发一条消息成功。
- 结构版本比代码新的 `chat.sqlite`（由测试用 `node:sqlite` 造出，属于外部输入）被拒绝，抛出的 `ChatStoreIncompatible` 带着文件路径，文件不被改动。

### 3.11 人类账号

- 两个人类账号都能读所有会话，包括两个 Agent 之间的私信；Agent 账号读不了它不在其中的私有会话（返回的结果和"会话不存在"无法区分）。
- 一个人类账号的已读位置前进，只出现在它自己的实时事件里，不出现在另一个人类账号的；新条目、会话变化、账号变化两个人类账号都收到。
- 实时事件里被过滤掉的事件不让游标停住：只有别人的事件时，读取返回的 `cursor` 仍越过它们；快照带 `me`。
- 每个人类账号有自己的未读摘要，一个人读消息不改变另一个人的未读数。
- 发给人类账号 A 的私信只推 A 的订阅；@ 了 B 的消息推 B 的订阅，不推 A 的；已停用的人类账号的订阅什么也收不到；另一个人类账号再订阅同一个 endpoint，订阅归到后者名下。
- Agent 账号不能用实时视图，也不能订阅推送（`human-only`）。
- `ensureAccount` 不允许改变已有账号的种类（`invalid-input`）。
- `findHuman` 按 handle（不分大小写）找人类账号，停用的也找到，Agent 的 handle 和不存在的 handle 都找不到。

## 4. Agent runtime

**边界：** `AgentRuntime` 接口，加上它发给模型提供商的 HTTP 请求和发给网关、聊天 app 的调用。

**替身：** 脚本化提供商、故障存储适配器、可控时钟、假聊天 app（或真实聊天 app）、假 node（经由真实网关，或直接用网关替身）。

### 4.1 loop 与上下文

- 提交一条输入后，模型被调用；模型发起工具调用，工具结果交回模型，直到模型给出最终回答。
- 模型的最终文字不会被发到任何聊天会话。
- 同一个 Agent 先后多次输入，模型每次看到的都是同一个上下文的延续：请求体的前缀逐次只增不改，包括关闭再打开 runtime 之后。
- 两个 Agent 的上下文互不可见。
- 上下文超过模型窗口时会自动压缩，压缩之后 Agent 能继续工作，压缩前的记录仍能通过历史工具读到。
- 提供商以"上下文太长"拒绝请求时，先压缩，再用摘要重试一次。
- 摘要请求失败或被截断时，不使用这个摘要，原上下文保持不变。
- 改了模型或 thinking 级别之后，下一次请求就使用新设置；正在进行的请求不受影响。

### 4.2 收件箱

- 同一个 `requestId` 提交两次，模型只看到一次。
- Agent 正在运行时，以 `steer` 提交的输入出现在当前这轮工具调用之后，不会另开一次 run。
- `withdraw` 一条还没交给模型的提交后，模型永远看不到它。

### 4.3 工具与崩溃

- 模型的工具调用参数还没有完整流完时就崩溃，重启后这个工具不会被执行。
- 有副作用、且没有声明可重做的工具（如 `bash`）在执行中崩溃，重启后不会重新执行，模型收到"已中断"。
- 聊天工具在执行中崩溃（聊天 app 已经发出消息，但工具结果还没提交），重启后重新执行，聊天 app 按 `requestId` 原样返回结果，频道里只有一条消息。
- `readUnread` 在同样的位置崩溃，重启后模型拿到的正是第一次读到的那一页。
- 工具调用的 `requestId` 来自 Durable 的工具调用 ID，而不是提供商的调用 ID：两次独立的工具调用即使提供商给了相同的调用 ID，也各自执行。
- 工作助手没有聊天工具：助手的工具列表里有工作区和历史工具，没有聊天工具；脚本化提供商让助手强行调用聊天工具名时，调用失败，聊天 app 没有收到任何调用。

### 4.4 关闭与重新打开

- `close()` 时正在进行的模型请求被中止：脚本化提供商观察到连接断开，迟到的回应不会产生任何效果。这一点要在请求的各个阶段都验证：发出前、等待响应头、流式传输中（文字和工具调用参数）、摘要请求中。
- `close()` 时正在进行的 node 工具调用被停止。
- 关闭后重新打开，未完成的工作从停下的地方继续，模型的上下文前缀不变。
- 观察（`watchEvents`）在 `close()` 和存储故障时都结束：每一个进行中的观察的 `ended` 都会完成。管理模块一侧，暂停、删除和关闭管理模块同样结束观察（`packages/admin/test/watch-ends.test.ts`）。
- 历史工具一页的序列化结果（含 JSON 外壳和转义）不超过 Durable 的 50 KB 上限：400 轮很短的工具调用之后 `history_read({from: 1})` 仍返回有效的 JSON，转义膨胀的超长记录被截断。
- 存储提交失败时，runtime 不会挂起：这次工作以失败结束（等待它的调用不再挂住，而是报错），runtime 调用一次 `onFatal` 后就死了；它不会自己重开，由 Agent Manager 关闭它，之后重新打开的 runtime 从存储里的状态继续，并能接收、回答新的输入。

### 4.5 工作助手

- 派生助手的工具调用崩溃后重做，不会派生第二个助手。
- 助手完成后，向派生它的对话汇报恰好一次；汇报在崩溃后不会重复，也不会丢失。
- 中断一个助手不影响别的助手，也不影响主对话。
- 关闭 runtime 时，主对话和所有助手一起停止；重新打开后，各助手继续各自原来的上下文。

### 4.6 提醒

- 设定的提醒到时间后，作为一条输入提交给主对话。
- 提醒在 runtime 关闭期间到期时，重新打开后立即触发，并且只触发一次。
- 提醒触发后在提交之前崩溃，重启后只触发一次。

### 4.7 用量

- 每次模型请求后，`usage()` 的数字增加；脚本化提供商返回的 token 数如实反映在里面。
- 不存在任何会因为用量过高而停止 Agent 的行为。

### 4.8 后台命令

- `bash` 带 `background: true` 时立即返回一个命令 ID；命令还在跑时，模型照常调用别的工具，这次 run 正常结束，runtime 变为空闲，命令没有被停掉。
- 命令结束后，结果作为一条输入（`requestId = command:<ID>`）提交给发起它的对话，模型恰好看到一次，里面有命令的输出。
- 模型读取汇报时进程死掉：重启后汇报既不丢失，也不重复。
- 命令执行中进程死掉：重启后汇报"已中断"一次，命令不会重跑，死掉的进程迟到的结果不会被汇报。
- 命令执行中 `close()`：node 上的这次调用被停止；重新打开后汇报"已中断"一次，再关闭、再打开也不会重跑。
- `bash_stop` 停止一条运行中的后台命令：node 上的这次调用被中止，结果回答"已停止"，再停一次回答相同；之后没有任何汇报。
- `bash_stop` 停一条已经结束的命令，回答它已结束；停一个不认识的 ID，回答没有这条命令；两者都不停任何东西。
- 工作助手启动的后台命令，结果汇报给这个助手，主对话看不到；助手对这条汇报的回答作为助手汇报到达主对话，恰好一次，助手读汇报时进程死掉也不丢不重。
- 前台命令不给 `timeout` 时，node 收到的时限是 10 分钟；给了的照原样；后台命令不给时，node 收到的调用没有时限。
- 前台命令的 `timeout` 超过 1 小时、后台命令的超过一天时，调用以错误结果返回，错误里写明上限，node 什么都没收到。

## 5. 连接器

**边界：** 输入是聊天 app 的 `inboxEvents` 和 `unreadSummary`，输出是对 runtime 的 `submit` 和 `withdraw`。

**替身：** 测试连接器时，用真实聊天 app 加上一个记录 `submit` 和 `withdraw` 的假 runtime；验证与 Durable 的组合时，用真实 runtime 加故障存储适配器。

- 一条新收件事件产生一条通知，`requestId` 是 `notice:<事件 ID>`，`whenBusy` 是 `steer`。
- 通知文字写明时间点、"至少"多少条、各时间线的条数、是否 @ 了你，以及"之后可能还有更多"。
- 已有一条通知还没交给模型时，又来了新事件：旧通知被撤回，新通知反映最新状态，模型最终只看到新的那条。
- 撤回时旧通知恰好已经交给了模型：新通知仍然照常提交，模型先后看到两条。
- 提交通知之后、保存事件位置之前崩溃：重启后重新提交同一个 `requestId`，模型只看到一次。
- runtime 关闭期间来了很多事件：重新打开后只产生一条通知，数字反映全部未读。
- 只有任务条目变化、没有新消息时，不产生通知。

## 6. Agent Manager

**边界：** `AgentManager` 接口和 `data/agents/` 目录。

**替身：** 真实聊天 app、真实 runtime、假的工作区宿主（按 node 和 Agent 记下准备和调用）、脚本化提供商。经真实网关和假 node 的部分（node 必须已配对、暂停停掉 node 上的命令）在第 10 节，因为把网关接成工作区宿主的是管理模块。

- 创建 Agent 后，聊天 app 里有对应账号，node 上有工作目录，`data/agents/` 里有它的文件。
- 工作目录建在创建时选的 node 上，Agent 的工作区工具在那个 node 上执行，别的 node 上没有。
- 重启后、暂停再恢复后，Agent 都接到创建时记在它文件里的 node。
- `describe` 对打开的和暂停的 Agent 给出同样的 node、设置和用量，只有状态不同。
- 暂停的 Agent 也能改设置；恢复后第一次模型请求就用新设置。
- 创建流程在改名之前的每一步之后中断，重做一遍都能得到完整的 Agent，不会出现两个聊天账号或两个文件；聊天 app 拒绝的创建（handle 被占用）原样拒绝，不算要重做的创建。
- 用已存在（打开的或暂停的）或已删除的 Agent 的 ID 创建被拒绝，名字、状态都不变；文件到位之后 runtime 打不开，Agent 保持关闭并被报告，`resume` 打开它。
- 文件改名之前中断：Manager 重启后看不到这个 Agent。
- 重启后，Manager 打开所有没有暂停的 Agent，跳过已暂停的。
- 对同一个 Agent 并发调用暂停、恢复、暂停，最终状态和这些调用按到达顺序依次执行的结果一致，并且任何时刻最多只有一个已打开的 runtime。
- 暂停后：模型请求被中止，node 上的工具调用被停止，之后发来的消息不会让模型被调用；恢复后，模型看到暂停期间累积的通知。
- 暂停状态在控制面重启后仍然保持。
- 删除 Agent 后，它的文件不存在，聊天账号被停用，它过去发的消息仍然可读。
- 一个 Agent 的存储文件损坏，其他 Agent 照常启动和工作。

## 7. Node 网关

**边界：** `NodeGateway` 接口，以及它对 node 说的 WebSocket 协议。

**替身：** 假 node、网络代理、可控时钟。

- 配对令牌只能用一次，过期后不能用；令牌只以哈希形式存储。
- 配对只新增 node：用有效令牌配对一个已配对的 node ID 被拒绝，原来的公钥照常认证，令牌没有被用掉。
- 已配对的 node 用签名认证；只有在控制面明确回答"不认识这个身份"之后，node 才会用配对令牌。
- 同一个 node 建立新连接后，旧连接被关闭，来自旧连接的消息一律被拒绝。
- `runTool` 把输出流式交给调用方，最后返回结果。
- 两个 Agent 在同一个 node 上并发调用，各自拿到自己的输出和结果：网关为每次调用生成自己的请求 ID。
- 调用没有自己的期限：时钟推进很久之后，node 送来的真实结果照常交给调用方。
- 调用方中止调用：网关立即以"已停止"（不是"结果未知"）结束它，并让 node 停掉这一次调用；之后 node 送来的输出和结果被丢弃。
- Agent ID 不合法的调用在发送和注册任何东西之前就被拒绝。
- 工具调用进行中连接断开：调用立即以"结果未知"结束；之后即使假 node 重连并送来这次调用的结果，也被丢弃，不会交给调用方。
- node 离线时调用 `runTool`，立即返回"节点离线"，不排队等待。
- `browse` 把 Agent ID 和路径交给 node，原样返回 node 的回答，列表和拒绝都一样；Agent ID 或路径不合法时什么都不发。
- node 离线时 `browse` 立即回答 `node-offline`；回答之前连接断开，同样立即回答 `node-offline`，之后迟到的回答不算协议错误，被丢弃。
- 另一个 node 送来某次浏览的回答（同一个请求 ID），不会交给调用方，调用方继续等自己的 node。
- 黑洞连接（TCP 没断但收不到数据，node 仍在发心跳）在心跳超时后被判定离线。
- 未认证的连接数量和消息大小（按序列化后的帧计）有上限；超限、格式错误或顺序错误（认证前发别的消息、重复认证）的连接被关闭，之后它送来的消息一律不读。
- 握手超时以协议错误（`gateway.error`）结束连接，不是身份拒绝。
- 一个 node 断开，不影响其他 node 上的调用。
- node 注册表存在 `control.sqlite` 里，和别的模块的表共处：别的模块的表在、版本不同，网关照常打开，重启后已配对的 node 照常认证，别的模块的数据不受影响，数据目录里除了 `control.sqlite` 没有别的文件；别的模块开着读事务时，网关照常配对 node。
- 网关自己的表版本不对，或者别的模块已经占了它的表名，网关拒绝启动，抛出的 `ControlStoreIncompatible` 带着 `control.sqlite` 的路径；别的模块照常打开。
- 一个模块的迁移列表从 `[v1]` 变成 `[v1, v2]` 后，下一次打开就升级已有的表，原有的行保留，别的模块的行不受影响；新建的存储和升级来的存储结构一样。
- 新的迁移失败时，整个事务回滚，存储留在旧版本，旧列表照常能再打开它，拒绝启动抛出的 `ControlStoreIncompatible` 带着文件路径。
- 存储里的版本比模块的列表新时拒绝启动，不改动存储。
- `Migrations` 本身：空列表、版本不严格递增的列表构造时报错；`after` 对新存储给出全部迁移，对已是最新的存储给出空，对更新的或不在列表里的版本给出"无法到达"。（`packages/migrations/test`）

## 8. Node

**边界：** node 进程对网关说的 WebSocket 协议，以及它在文件系统和进程上的实际效果。测试在真实 Linux 上运行（`pnpm test:linux` 在 Linux 容器里以非 root 账号运行，macOS 上只跑不依赖 Linux 的部分），以子进程启动 node。

**替身：** 假网关。

### 8.1 命令

- 命令原样交给 `/bin/sh -c` 执行，工作目录和 HOME 是该 Agent 的工作目录。
- Agent 自己写的 `sudo` 原样执行，成败由宿主决定；node 从不自己加 `sudo`。
- 返回的结果如实区分：正常退出（附退出码）、被信号终止、超时被杀、没能启动（例如工作目录不存在）。
- 输出超过上限时截断，并在结果里标明。
- `timeout` 超过协议规定的、这个模式的上限时（前台 1 小时，后台一天），命令不执行，返回参数错误；后台命令可以要超过 1 小时的时限。
- 命令退出后，后台子进程仍占着输出管道：node 不会一直等下去，在短暂等待后返回，并标明输出可能不完整。
- 进程组里只剩僵尸进程时，算作已经结束。
- 记录下来的 PID 被系统复用给别的进程后，停止操作不会误杀那个进程。

### 8.2 文件

- 文件工具（`read`、`write`、`edit`）的行为与 Durable 自带工具在本地执行时一致。
- 以两个点开头的普通文件名（`..notes.md`、`...`、`..cache/x.txt`）照常读写。
- 路径不能逃出工作目录：`..`、指向工作目录外的绝对路径、指向外部的符号链接都被拒绝。（Durable 的文件工具内部会把路径先变成绝对路径再解析，所以指向工作目录内的绝对路径照常可用。）
- 读取时文件被别人修改，返回"文件已改变"，而不是拼接出新旧混合的内容。

### 8.3 连接与停止

- 连接断开时，正在运行的、由工具调用启动的进程组被停止。
- 网关停止一次调用，只杀掉这次调用的进程组，同一个 Agent 和其他 Agent 的其他调用照常运行。
- 命令已经返回、后台进程还占着输出时收到停止，后台进程也被杀掉。
- 通过真实网关：调用方中止调用后，node 上这次调用的进程组消失，调用方得到"已停止"；另一个 Agent 的并发调用不受影响，拿到自己的结果。
- node 自己关闭时，停止所有它启动的进程组，包括命令已经返回、但还留着后台进程组的那些。
- 修改或删除工作目录里的 `MEMORY.md`，不影响之后的命令执行。
- 工作目录不存在时，工具调用以明确的错误失败，node 不会自己重建它。
- 身份被拒绝时，node 退出，退出码是用户服务不会重启的那个（§9），不会无限重试；网络失败或网关以协议错误（例如握手超时）结束连接时，按退避重连。

### 8.4 浏览工作区

- 目录按名字列出条目，文件带大小，指向工作目录内的符号链接列为符号链接，经它浏览照常可用；指向工作目录内的绝对路径照常可用；以两个点开头的名字是普通名字。
- 文件返回开头的文字；超过上限时只返回上限以内、截在完整字符处的部分并标明截断。条目超过上限的目录同样只返回上限条并标明截断。含 NUL 字节的文件只报告大小。
- 路径不能逃出工作目录：`..`、指向工作目录外的绝对路径、指向外部的符号链接（目录或文件）、悬空的符号链接都以 `outside-workspace` 拒绝；浏览前后工作目录内外都没有变化。
- 不存在的路径、工作目录不存在时以 `not-found` 拒绝，node 不重建工作目录；FIFO 以 `unreadable` 拒绝，不会一直等写入方。
- 经真实网关：浏览能列出和读取真实工作区，拒绝指向外部的符号链接；node 停下后回答 `node-offline`。

## 9. Node 管理 CLI

**边界：** `mate node` 命令行，以及它读的发布包和它留在 HOME 里的文件（布局见 DEPLOYMENT §3.2）。测试以子进程运行 CLI，不 import 它的内部文件。

**替身：** 放在 PATH 上的假 `systemctl` 和假 `journalctl`（记录参数，按测试设定的状态回答，像真的用户管理器一样根据单元文件是否存在回答 `LoadState`），临时目录作为 HOME，测试自己写的发布包（和发布构建同一格式：ustar 归档、`mate-node/` 下的文件、清单、`.sha256`）。macOS 和 `pnpm test:linux` 都跑。

**没有可续做的状态机（ARCHITECTURE §11 第 1 条）。** 每个命令只看现有状态：程序目录（不存在 / Mate 的某个版本 / 没有清单，不是 Mate 的）、`~/.local/bin/mate` 和单元文件（不存在 / Mate 的 / 别人的）、服务状态。所以"中断后重跑"的测试构造的是中断可能留下的状态（程序目录已挪开但新的还没放好、半个暂存目录、单元已删程序还在），再加一个在解包中途真的 SIGKILL 的测试。

- 首次 `install` 放好程序目录、`mate` 命令和单元文件，不启用也不启动服务；`start` 之后服务被启用并运行。没有配置时 `start` 拒绝。
- 重复 `install` 什么都不改，也从不启动、重启或启用服务，不管服务在运行还是被管理员停掉。
- 已装了另一个版本时 `install` 拒绝（提示用 `update`），不做任何改动。
- `update` 在服务处于 `active`、`activating`、`deactivating`、`reloading` 时拒绝，不做任何改动。
- `update` 在服务停止时换上新版本，服务保持停止；配置、身份、工作区逐字节不变。
- `update` 死在"旧程序目录已挪开、新的还没放好"之间，或留下半个暂存目录，重跑同一个命令完成更新，不留下暂存目录。
- `update` 在校验或解包发布包时被 SIGKILL，已装的程序目录原样不变；重跑完成更新。
- `uninstall` 停用并停止服务，删除程序目录、`mate` 命令和单元文件，保留配置、身份和工作区；再跑一次报告没有可删的东西，不改动任何文件。
- `uninstall` 死在"单元已删"或"删程序目录到一半"之后，重跑完成卸载。
- 程序目录里有 Mate 没装的文件或目录时，`update` 和 `uninstall` 拒绝，列出它们，不做任何改动；`status` 也报告它们。
- 不是 Mate 写的单元文件和不是 Mate 的 `~/.local/bin/mate`，`install` 和 `uninstall` 都不碰，并在输出里报告；`uninstall` 对这样的单元定义的服务也只读状态，不停用它。
- 发布包校验和不对、缺 `.sha256`、含符号链接、硬链接、特殊文件、含 `..` 的路径、绝对路径、`mate-node/` 之外的路径、清单没列的文件、缺清单列的文件、为别的平台构建时，拒绝；已安装的东西不变，首次安装不留下任何文件。
- 没有用户管理器时，`install`、`update`、`uninstall` 拒绝，不做任何改动。
- 管理命令以 root 运行时拒绝（Linux 上用 `unshare -r` 得到 UID 0）。`node run` 不检查，它只由用户服务启动。
- `configure` 写出权限 0600 的配置；不带 `--pairing-token` 再写一次就去掉令牌；地址不是 http(s)/ws(s) 时拒绝，原文件不变。
- `status` 报告版本、服务状态和配置，不打印配对令牌。
- `logs` 读这个服务的用户日志，`--follow` 时跟随。
- 没有配置时 `node run` 的退出码在单元文件的 `RestartPreventExitStatus` 里；身份被拒绝时也用这个退出码（§8.3 的退出测试）。

发布构建本身（`pnpm bundle:node`）不在测试套件里，因为它要下载官方 Node。`deploy/node/smoke-test.sh` 在干净的 Debian 13 和 Ubuntu 24.04 容器里用普通账号装真的发布包，走一遍安装、配置、状态、`node run`、卸载，并用 `systemd-analyze verify` 检查单元文件。

## 10. 管理模块

**边界：** 管理模块的接口，以及它的 HTTP 路由（经 Web 外壳）。

**替身：** 真实 Manager、runtime 和聊天 app，真实网关加假 node，脚本化提供商（凭据的 `baseUrl` 指向它）。

- 设置模型时，只接受该提供商已经配置了 API key 的模型；不支持的 thinking 级别直接被拒绝，不会被悄悄降级。
- 模型列表只列已经存了 key 的提供商的模型，每个带它接受的 thinking 级别。
- 修改 API key 后，下一次模型请求使用新 key；用同样的值再保存一次，不会打断正在运行的 Agent。
- key 跨重启保存，列出时只显示末四位。
- 查看对话记录时，能实时看到流式输出和工具调用；查看不会改变 Agent 的任何状态。
- 能按名字查看工作助手的对话；没有这个助手、或 Agent 没有打开时拒绝。
- 浏览工作区在 Agent 自己的 node 上进行，返回 node 的结果，别的 node 不被询问；暂停的 Agent 也能浏览，浏览不改变它的状态。node 拒绝的路径（比如逃出工作目录的）以 node 给的原因拒绝；node 离线时以 `node-offline` 拒绝；不存在的 Agent 和不合法的路径在询问 node 之前被拒绝。路径限定在工作目录里由 node 保证，在 8.4 测。
- 配对 node：生成的令牌只能用一次。
- 创建 Agent 时不合法的名字或 handle 以 `invalid-input` 拒绝，handle 被占用以聊天 app 的 `handle-taken` 拒绝（不是创建中途失败），已存在的 ID 以 `agent-exists` 拒绝；都什么都不创建。暂停、恢复、改设置排在删除之后得到 `unknown-agent`；观察或查助手时 Agent 被暂停，得到 `agent-closed`。
- 创建 Agent 时 node 必须已经配对，否则拒绝，聊天账号和文件都不会出现；工作目录建在所选 node 上，Agent 的命令在那里执行，控制面重启后仍然在那里。
- 暂停 Agent 时，node 上进行中的命令经真实网关被停止；恢复后模型得知这次调用没有完成，命令不重跑。
- 列出 Agent 时，显示名和 handle 来自聊天账号，node、状态、设置和用量来自 Agent 文件；一个 Agent 的文件读不出来时，它以"读不出"和原因列出，可以删除，其他 Agent 照常列出。

## 11. Web 外壳

**边界：** HTTP 接口，加上浏览器里的页面行为。页面测试用浏览器测试工具（如 Playwright），驱动真实的前端和后端，后端的模型用脚本化提供商。

### 11.1 后端

- 未登录访问 API 返回 401，访问页面跳转到登录页，并带上原本要去的地址。
- 登录后的跳转只接受站内 `/app` 路径。
- 连续输错密码不会把人类锁在外面；同时进行的密码校验最多 2 个，多的排队而不拒绝：几个客户端循环输错密码时，正确的密码仍然被检查并登录成功；队列满（64）时返回 429，排队超过 10 秒的也返回 429。
- 初始密码文件只在第一次启动时读取。
- 第一次启动按 `MATE_INITIAL_HANDLE` 建一个管理员（不给时叫 `admin`），这个管理员用 handle（不分大小写）加初始密码登录；重启不会多出一个人类；初始 handle 不合法时拒绝启动。
- 密码错、handle 不存在、handle 是 Agent 的、人类已被停用，这四种登录得到完全相同的拒绝（状态码和正文相同，不设 cookie）。
- 会话令牌只以哈希形式存储；退出登录后这个令牌立即失效。
- 登录会话 30 天后过期，跨重启保留；第一次启动（还没有任何人类）没有初始密码文件时拒绝启动。
- 事件流从快照的游标起送出之后提交的变化，每批的 SSE id 就是这一批读到的游标（`liveEvents` 返回的 `cursor`）：带着 `Last-Event-ID` 重连，从断开处接着读，不重复也不遗漏。每批带这个人类自己的未读摘要。
- 游标接不上时，事件流发出"需要重新拉快照"并关闭；没有游标或没有登录时，事件流在开始之前就被拒绝。
- 退出登录后，事件流在下一个事件之前发出"需要登录"并关闭，之后的消息不再送出（3.9 的最后一条是会话过期时的同一件事）。
- 带人类 cookie 但声明为 `text/plain` 等的请求体回 415，什么都不改；非 GET 请求的 `Origin` 不是本服务器时回 403（登录也一样），自己的 `Origin` 和没有 `Origin` 放行；路径参数的百分号编码不合法回 400。
- 拒绝的状态码：`archived` 409、`not-member` 403、`handle-taken` 409（没有 `agentId`）、`agent-exists` 409、`outside-workspace` 403、`unknown-agent` 404；创建在 node 准备工作区时失败回 500 `creation-failed` 带 `agentId`，带着它重做得到同一个 Agent。
- 观察 Agent 的事件流同样只活在登录会话期间：会话过期，或退出登录后的下一次心跳，发出 `login` 并关闭。
- 同一个 requestId 重发消息只产生一条消息；聊天 app 和管理模块的拒绝按 reason 对应固定的状态码，带着 reason 返回。
- 组装起来的控制面：经 HTTP 配对的 node 上创建的 Agent 能回复管理员的私信，这条回复推送到管理员经 HTTP 订阅的浏览器，并出现在事件流里；观察 Agent 的事件流第一批是快照，Agent 暂停时以"已结束"关闭。
- VAPID 公钥、Agent、node 和 API key 跨重启保留。
- 前端目录里的文件不需要登录，`/app` 下的页面需要；其他页面路径回前端的入口页；路径逃不出前端目录。没有前端时页面回 404，API 照常。node 的 WebSocket 只在 `/api/nodes/connect` 上接受。
- 控制面在**存储夹具**（整个数据目录的副本）上启动：原来的所有者成为管理员，用 handle `owner` 和 `facts.json` 里的密码登录（别的密码被拒，也没有多出别的人类），名字不变，看到夹具里的会话和未读摘要，并能发消息；alpha.2 签发的登录会话 cookie 升级后仍然有效；这个账号能改名、改 handle、添加别的人类；夹具里的 Provider 凭据还在，夹具里的配对令牌仍能配对一个 node。

### 11.2 人类：角色、自己的资料和管理

测试里 `HumanBrowser` 用 handle 加密码登录；测试环境的第一个人类是管理员 `admin`。

- 管理员添加普通人类；同一个 `requestId` 重发返回同一个人类，不会多出第二个；添加用的 handle 已被占用时回 409 `handle-taken`，什么都没创建；密码短于 12 字节回 400。
- 普通人类登录后读到每一个会话（包括管理员建的私有频道）和它的历史；调用 `/api/admin/*` 和 `/api/humans` 一律回 403 `admin-only`，连请求体都不看。
- 每个人类以自己的身份行事：普通人类发的消息，作者是这个普通人类自己的账号；其未读和管理员的未读各是各的，各读各的位置。
- 人类改自己的显示名和 handle，之后用新 handle 登录，旧 handle 不能再登录；改成别人的 handle 回 409，空名字回 400，什么都没改。
- 改自己的密码需要当前密码（不对回 403 `wrong-password`），新密码至少 12 字节；改完这个人其他的登录会话结束，当前这个继续有效，新密码生效。
- 管理员重置某个人类的密码：那个人类所有的会话结束，管理员的会话不受影响，新密码生效。一个已在密码校验队列里等待的登录，如果等待期间密码被重置，即使它检查的是旧密码也被拒绝（401），不留下会话。测试做法：用若干个并发的错密码登录占满校验队列，等该登录进入队列（`ObservedClock`），重置密码后再让队列走完。
- 改角色结束那个人类所有的登录会话（会话是权限的快照）：升为管理员的普通人类和降级的管理员，旧 cookie 都回 401，重新登录后得到新角色的权限，改角色的管理员自己的会话不受影响；管理员开着的 Agent 事件流在被另一个管理员降级后，下一次心跳以 `login` 结束。
- 最后一个有效的管理员不能被降级或停用（409 `last-admin`，什么都不改）；另一个人类升为管理员之后，原来的管理员可以被降级，而新的唯一管理员又不能被停用。
- 停用一个人类：这个人开着的实时事件流在下一个事件前以 `login` 结束，之后不能再登录，其消息仍然可读，重复停用什么都不改，列表里其 `active` 为 `false`。
- 对不是人类的账号 ID 做角色、密码或停用操作回 404 `unknown-account`。

### 11.3 前端

- 打开页面时选中的频道，在事件流建立之前就已确定：建立事件流时立即到达的消息不会丢失。
- 重放或重复的事件不会产生重复消息，也不会让讨论串的回复数虚增。
- 切换频道后，旧频道迟到的响应不会覆盖新频道的内容。
- 消息发送过程中又输入的文字，在发送成功后仍然保留。
- 发送请求的响应丢失后重试，不会产生重复消息（同一个请求 ID）。
- 收到"需要重新拉快照"后，页面重新加载状态，而不是停住。
- 会话过期时跳转到登录页，登录后回到原来的位置。
- 从推送通知点进来，直接定位到那条消息；消息不存在时，退回到最新消息，并显示提示。
- 手机宽度下可用。
- 管理员在人类页添加一个普通人类；这个人在另一个浏览器里登录，能聊天，导航里没有"管理"，直接打开管理地址看到"需要管理员权限"。
- 退出登录（个人资料页或导航菜单）先取消这个浏览器的推送订阅，再结束登录会话，所以同一个浏览器上下一个登录的人类不会收到上一个人类的通知；取消订阅失败时仍然退出。测试用往页面注入的脚本假装浏览器已订阅，检查发出的取消订阅请求和随后的登录页。
- 人类在个人资料页改显示名和 handle：导航立即显示新名字，用新 handle 能再登录；改成被占用的 handle，在 Handle 字段下显示"已被占用"。
- 改密码时当前密码不对、新密码太短都在字段下显示；改对之后当前登录继续有效，新密码能登录。
- 最后一个管理员被降级时页面显示"必须至少保留一个有效的管理员"；停用先弹确认，取消什么都不变，确认后那一行显示"已停用"。

**实现。** `apps/web/test/*.test.ts` 在 vitest 里把 Playwright 当库用（无头 Chromium）。每个 worker 用 Vite 的 `build()` 把前端构建一次到临时目录，作为 `webDirectory` 交给进程内启动的真实控制面（可控时钟，Agent 用假 node 和脚本化提供商）。浏览器走 `localhost`，因为 `__Host-` 的 Secure cookie 只在安全上下文里保留。拿不到的网络行为用 Playwright 的路由截获（挂起一个响应、丢掉一个响应、让事件流发 `resnapshot`），重放事件用往页面注入一个让每批事件重复投递的脚本。聊天（会话、未读、讨论串、任务、搜索、历史翻页）、管理（提供商、node 配对、创建 Agent 与私信、观察、工作区、设置、暂停恢复删除）和人类（添加、个人资料、改密码、最后一个管理员、停用）各一个文件。Web Push 的订阅和系统通知依赖浏览器的推送服务，无头环境里没有，不在这里测（退出登录时的取消订阅除外：页面里注入一个假的订阅，只看发给控制面的请求）；通知点开后的定位用同一个地址测。

## 12. 系统场景

少量端到端测试，把整个系统当作一个模块：以真实子进程启动控制面和 node，模型用脚本化提供商，管理员的操作通过 HTTP 发出。它们证明各模块确实接在了一起；具体的边界情况应当在各模块的测试里覆盖，而不是在这里。

1. 管理员在频道里 @ 一个 Agent，Agent 读取后回复。
2. Agent 运行一条长命令期间，管理员又发了两条消息：Agent 收到一条通知，读到两条消息，完成命令后回复。
3. Agent 读完频道后、发言前，管理员又发了一条：Agent 的发言被拦下，它重新组织内容后再发。
4. Agent 执行命令期间控制面被 SIGKILL，然后重启：这条命令不会被再次执行，Agent 收到"已中断"，并继续工作。
5. Agent 执行命令期间 node 网络断开：Agent 收到"结果未知"，继续读写消息；node 恢复后，新的命令正常执行。
6. 管理员暂停一个正在运行的 Agent，再恢复：暂停期间模型没有被调用，恢复后 Agent 处理积压的通知。
7. 两个 Agent 在私信里协作：A 派一个任务给 B，B 认领并完成，A 收到通知。
8. Agent 派生一个工作助手执行命令，助手完成后汇报，Agent 把结果发到频道。

**实现。** 八个场景在 `tests/system/test/`（pnpm 包 `@mate/system-tests`，根 `vitest` 的 include 里有 `tests/*/test`）：场景 1 到 3 在 `chat.test.ts`，4 到 6 在 `recovery.test.ts`，7 和 8 在 `agents.test.ts`，进程夹具在 `support.ts` 的 `startSystem()`。每个场景一个测试，名字以场景号开头。

- 控制面用 `node --conditions=mate-source apps/control-plane/src/main.ts` 启动，环境变量同部署；node 用 `mate node run`，HOME 是临时目录，配置里的配对令牌来自管理员经 HTTP 生成的令牌。模型提供商的凭据由管理员经 HTTP 保存，`baseUrl` 指向这个进程里的脚本化提供商。管理员用 `HumanBrowser`（`@mate/testkit`，控制面测试共用）。
- 不用 sleep。等待的都是可观察的状态：长命令在 Agent 的工作区里写 `started`，测试看到它才继续，要它结束时写 `release`；其余是轮询 HTTP（node 在线、频道里出现某条消息）。要卡在某个时刻的事（场景 3 里管理员在 Agent 读完之后、发言之前写）放在脚本化提供商的步骤里做：步骤收到请求时，先让测试发 HTTP，再给出回答。
- 场景 4：看到 `started` 后 SIGKILL 控制面，在同一个数据目录和端口上重启；命令把自己的运行次数追加到 `runs.log`，Agent 重启后用 `cat runs.log` 确认只有一次。node 的重连是真实的退避重连。
- 场景 5：node 经网络代理连到控制面，用 `disconnect` 模式断开（`blackhole` 要等 30 秒的心跳超时，且走的是同一条"连接丢失"路径）；断开时命令在网关的在途调用上以"结果未知"结束，node 停掉命令的进程组，恢复后 node 重连，新命令正常执行。
- 场景 6：暂停后命令的进程消失；"暂停期间模型没有被调用"由恢复后的那一步断言（恢复请求发出之前它不能被请求到），脚本外的请求本来就会让 `assertComplete()` 失败。
- 场景 7 和 8 用多条 lane 区分 Agent 与工作助手，用 promise 门控让"先发生"的事真的先发生（B 在 A 建好任务之后才读；助手在主对话收到派生结果之后才干活）。
- 不依赖 Linux 的行为，macOS 和 `pnpm test:linux` 都跑；一个场景起一套进程，整组约 5 秒。
- 变异检查（临时改接线，确认场景失败，已还原）：把 `bash` 改成可重做，场景 4 失败；把聊天发送的 `freshness` 改成 `false`，场景 3 失败；把连接断开的结果从"未知"改成"离线"，场景 5 失败。

## 13. 部署冒烟

**边界：** 发布的东西本身：控制面镜像、`deploy/control-plane/` 的两个 Compose 文件、node 发布包。`pnpm smoke:deploy`（`deploy/smoke.ts`）需要 Docker，不在 `pnpm check` 里，发布前手动跑，或对已构建的镜像设 `MATE_SMOKE_IMAGE` 跑。

**替身：** 脚本化模型提供商跑在宿主上，容器经 `host.docker.internal` 和一个监听 `0.0.0.0` 的中继到达它。其余都是真的：用宿主账号的 UID/GID 起 Compose 项目，node 在普通的 Debian 13 容器里由发布包安装（systemctl 是只回答"未运行"的替身，同 §9），管理员的操作通过 HTTP 发出。

- 镜像非 root 运行，用 `compose.yaml` 加 `compose.initialize.yaml` 在 0700 的绑定挂载目录上起来，健康检查转为 healthy。
- 先用 `sha256sum -c` 校验发布包，再用包里的 CLI 安装、配置，`node run` 用配对令牌连上，网页接口看到它在线。
- 管理员保存提供商凭据，在这个 node 上创建 Agent，私信它，Agent 读取并回复。
- `docker compose stop` 在 Compose 的 10 秒期限内以退出码 0 结束，日志里有 SIGTERM 的收尾。
- 只用 `compose.yaml` 重新启动：存下的密码仍能登录，Agent 重新打开，私信还在，node 重新连上。

冒烟默认跑 Docker 宿主的架构；`MATE_SMOKE_ARCH=x64` 或 `arm64` 改跑另一种，靠宿主的仿真。冒烟不覆盖：前端（镜像里的页面目录没被访问）、反向代理和 HTTPS。
