# 长会话工具身份查询基准（#162）

`AgentSession.toolAction(agentId, identity)` 为恢复后的工具调用找回已确认 assistant 中的原名称、参数和 action scope（产生该调用的消息 delivery ID）。旧实现调用 `read()`，每次先解析当前 Agent 的全部消息与最新压缩点，再寻找调用；早命中也付出完整解析成本。

## 重现

```sh
pnpm build:control-plane
node apps/control-plane/benchmarks/tool-action.mjs > /tmp/tool-action-result.json
```

基准脚本只建立、读写、清理自己的临时合成 SQLite 数据库，不连接供应商或运行 Agent 命令。原版证据在 [tool-action-baseline.json](tool-action-baseline.json)，查询缩小后的证据在 [tool-action-scoped.json](tool-action-scoped.json)；文件含每次测量值和源码 SHA-256。提交 `f550e08f` 保存了脚本、原版生产代码与基线，可在该提交的独立 checkout 安装依赖、构建后运行相同命令。

环境为 Apple M2 Pro、macOS Darwin 24.6.0 arm64、Node v24.21.0、SQLite 3.53.4；使用文件数据库、WAL、外键检查。每组分别建立 100 / 1,000 / 10,000 条固定合成消息，以 user、assistant tool call、toolResult、assistant text 四条为循环，正文含固定中文文本。所有 assistant 工具调用重复使用同一原始 Pi toolCallId，但 assistant 记录 ID 不同。多 scope 组每 100 条一 scope，另一组全部属于同一 scope（因此 100 条时两组结构相同）。

早命中位于第 2 条，晚命中位于倒数第 3 条；未命中分别使用最后一个真实 scope 内不存在的 hash，以及完全不存在的 scope。每情形预热 10 次，测量 50 次完整同步 `toolAction` 调用；不计建库、写入、身份构造和结果断言。中位数与 p95 为最近秩统计。另一次不计时调用临时统计 `JSON.parse` 调用数及传入字符串的 UTF-8 字节数，再恢复原函数，避免该统计影响耗时。解析计数不是 SQLite 内部扫描行数或磁盘读取字节数。

10,000 条多 scope 的晚命中从 85.80 ms 降到 6.90 ms，解析从 10,000 条 / 18,468,612 字节降到 98 条 / 181,018 字节；该组 scope 内未命中解析 100 条 / 184,700 字节。早命中只解析前两条 / 3,697 字节，不存在的 scope 不解析 JSON。

保留最小方案：从当前真实 durable identity 格式提取 UUID scope，SQL 同时限制调用者 Agent、scope 和消息类型，按 seq 迭代候选并在命中后停止。scope 仅用于筛选；每个候选仍从已确认 assistant 原记录完整重算 `mate:<scope>:sha256([assistantId,callId]):1`，原记录继续提供名称和参数。没有更改身份生成、收据、压缩、调度、表结构或数据库格式；没有缓存或新增索引，因而不引入迁移或接受其他数据库版本的路径。

SQLite 查询计划仍为 `SEARCH owner_agent_session_records USING INDEX owner_agent_session_records_agent (agent_id=?)`。现有索引只定位 Agent，不能直接跳到 scope；SQLite 仍可能扫描这个 Agent 的全部记录并检查 scope。10,000 条不存在 scope 的请求虽不解析 JSON，仍约需 6.11 ms。这里不把 JavaScript 解析减少宣传为数据库常数时间查询。

长单 scope 的晚命中仍解析 9,998 条 / 18,464,930 字节，中位数从 83.63 到 80.65 ms；未命中仍解析 10,000 条 / 18,468,612 字节，83.11 到 80.76 ms。这种情况保留线性成本，未证明有显著改善。普通 scope 索引也不会减少这个 scope 内候选，当前证据不值得因此增加数据库格式变更。

本次基线早期样本波动明显（10,000 条多 scope 早命中 p95 432.94 ms），共享开发机的负载、垃圾回收和缓存状态都会影响耗时。不能将两次顺序测量的精确倍率推广为 VPS 容量承诺；减少解析量是可确定的结果，延迟是本机温热合成工作负载的观察。没有测量真实 VPS、冷磁盘、真实模型能力或供应商吞吐；耗时不作为 CI 门槛。

## 语义与恢复验证

`agent-session-tool-action.test.ts` 通过公共 `append` / `context` / `toolAction` 边界保存合成记录，覆盖早晚/未命中、相同 Pi toolCallId 在同 scope 与跨 scope 重复、其他 Agent、伪造 scope/hash 和畸形身份；压缩并关闭重开数据库后，旧调用仍返回原名称与嵌套参数。这些保持既有语义的回归用例在改代码前和改后均通过；性能问题的改前证据来自上述完整调用基准，没有人为制造功能失败或脆弱的计时断言。现有工具执行、操作收据和重启恢复测试继续负责副作用不重放及参数冲突拒绝。
