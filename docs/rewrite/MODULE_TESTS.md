# Mate 模块边界测试说明

> 配套文档：[ARCHITECTURE.md](ARCHITECTURE.md)。读这份之前请先读架构文档的第 2、4 节。

## 1. 规则

1. **只测模块边界，不写单元测试。** 测试只通过模块对外的接口（架构文档第 4 节列出的方法、HTTP 路由、WebSocket 协议、CLI 命令）驱动模块，只断言从接口上能观察到的结果。不 import 模块内部文件，不检查内部表结构，不 mock 模块内部的函数。
2. **边界外的依赖用替身。** 替身只能替换另一个模块或外部系统，不能替换被测模块自己的一部分。第 2 节列出允许的替身。
3. **失败和恢复路径与正常路径同等重要。** 每个模块都要覆盖：调用方重复调用、中途崩溃后重启、依赖方不可用。只跑通正常路径不算验收。
4. **测试要能说明"为什么"。** 每个测试名用一句完整的话描述行为，例如"同一个 requestId 重复发送只产生一条消息"。
5. **模型不是被测对象。** 模型由脚本扮演，测的是"模型做出某个选择之后，系统能否正确兑现"。不测模型会不会做出那个选择。
6. **假实现和真实集成要分得清。** 用了替身的测试不能叫"集成测试"。真实提供商和真实 VPS 的检查不在本文范围内。

## 2. 替身与测试工具

这些工具本身也是要写的代码，并且优先实现，因为后面每个模块的测试都依赖它们。

| 名称 | 替代什么 | 能力 | 用于 |
|---|---|---|---|
| **脚本化提供商** | 模型提供商 | 本地 HTTP 服务，按真实提供商协议（先做 OpenAI Responses）返回 SSE。脚本由命名步骤组成，每步收到真实请求体，可以回答文本、发起工具调用、只发一半、卡住不回、返回 4xx/5xx。按会话 ID 区分不同 Agent 的请求。`assertComplete()` 检查：没有用完的步骤、没有多余的请求、没有未声明的取消，任何一项不满足都报错，并写明是哪个 Agent 的哪一步 | runtime、系统场景 |
| **可控时钟** | 系统时间 | 测试推进时间，触发定时器 | runtime（提醒）、聊天 app（推送退避）、网关（心跳） |
| **故障存储适配器** | Durable 的 SQLite 适配器 | 包装真实的 SQLite 适配器，可以在第 N 次提交之前或之后让提交失败或挂起，用来模拟"写到一半崩溃" | runtime、连接器 |
| **假 node** | node 进程 | 实现 node 的 WebSocket 协议，测试控制工具调用：返回结果、流式输出、挂起、断开连接 | 网关、runtime、Manager |
| **假网关** | 控制面的 node 网关 | 实现网关一侧的协议：配对、认证、发送工具调用、断开连接 | node |
| **假聊天 app** | 聊天 app | 只在 runtime 的测试里使用，实现 `ChatApp` 接口里聊天工具用到的那部分，并记录收到的调用 | runtime（只测工具转发时） |
| **网络代理** | node 与控制面之间的 TCP 连接 | 三种模式：转发、黑洞（吞掉数据但不关闭连接）、断开 | 网关与 node 的心跳和重连 |
| **假 systemd** | `systemctl`、用户管理器 | 放在 PATH 上的假命令，按脚本返回服务状态，并记录被调用的参数 | node CLI |
| **进程夹具** | 无 | 以真实子进程启动控制面或 node，能 SIGKILL 后在同一个数据目录上重启 | 系统场景 |

**崩溃怎么模拟：** 优先用故障存储适配器，在进程内让提交在指定点失败或挂起，然后关闭并重新打开模块，比如重新调用 `AgentRuntime.open`。少数必须验证"进程真的死了"的场景用进程夹具 SIGKILL。不使用 eval 字符串或全局变量注入故障。

## 3. 聊天 app

**边界：** `ChatApp` 接口。测试用临时目录里真实的 `chat.sqlite`，不用替身。推送用一个记录请求的假推送服务。

### 3.1 账号与会话

- `ensureAccount` 用同一个 `externalId` 调用两次，返回同一个账号。
- 公开频道不加入也能读，但不能发言、建任务或上传附件。
- 私有频道和私信只有成员能读；非成员读取时，返回的结果和"会话不存在"无法区分。
- 两个账号之间只有一个私信会话，不管谁先打开。
- 不能和自己打开私信。
- 所有者账号能读所有会话，包括两个 Agent 之间的私信。
- 邀请立即生效；被邀请者的已读位置从加入时开始，加入之前的历史不算未读。
- 已归档的频道可以读，但不能发言或上传附件。

### 3.2 发送与新鲜度

- 自上次读取以来没有别人的新消息时，发送成功。
- 有别人的新消息时，不发送，结果里带上这些新消息，并推进发送者的已读位置；紧接着原样再发一次，发送成功。
- 自己发的消息不会让自己被拦下。
- 新加入频道的账号第一次发言会被拦下，结果里带上频道最近的消息。
- 讨论串里的回复只检查这个讨论串；在顶层发言不会因为讨论串里的新回复被拦下。
- 别人在同一条时间线上新建或认领了任务，发送同样会被拦下，结果里带上这个任务变化。
- 被拦下的发送在聊天 app 里不留下任何痕迹：没有消息、没有收件事件、没有推送。

### 3.3 读取

- `readUnread` 返回已读位置之后的消息，并推进已读位置。
- 未读超过预算时，返回最新的、放得下的消息；结果写明未读总数、返回的序号区间、跳过的序号区间，以及跳过区间里 @ 了读者的消息的序号。读完后已读位置在最新一条。
- 预算按字符数和附件大小一起计算：一张大图片也会占掉预算。
- `readHistory` 和 `search` 不改变已读位置。
- 同一个 `requestId` 调用两次 `readUnread`，即使第一次之后又来了新消息，第二次也原样返回第一次的那一页。
- 一个讨论串的已读位置和它所在频道的已读位置互相独立。

### 3.4 幂等

- 同一个 `requestId` 发送两次，只产生一条消息、一组收件事件和一次推送，第二次返回和第一次一样的结果。
- 同一个 `requestId` 但内容不同，第二次被拒绝，并且不产生任何变化。
- 被拦下的发送也存回执：同一个 `requestId` 再来一次，返回同样的"被拦下"结果，而不是这次发出去。（让模型改了再发时必须用新的 `requestId`，这由 Durable 的工具调用 ID 自然保证。）
- 所有者在网页上用同一个请求 ID 重发，不会产生重复消息。

### 3.5 原子提交

- 消息、收件事件、推送队列、随消息创建的任务和实时事件，要么全部存在，要么全部不存在。非法参数（比如任务标题非法、@ 了不存在的账号）在写入开始之前就被拒绝，造不出写到一半的失败，所以测试做法是：从另一个连接给同一个 `chat.sqlite` 加一个触发器，让这次发送最后写的那一行（回执）失败，断言消息、任务、收件事件都不存在，也没有收件信号。

### 3.6 收件事件与未读摘要

- 频道顶层消息为作者以外的每个成员各产生一条收件事件。
- 讨论串回复只为关注这个讨论串的人（根消息作者、回复过的人、在讨论串里被 @ 过的人）产生收件事件；离开私有频道的人不再收到。
- 收到某条时间线收件事件的账号，未读摘要里正好列出这条时间线，未读数与收到的事件一致。
- 发消息之后才加入的成员，不会收到这条消息的收件事件。
- 任务条目不产生收件事件。
- 收件事件的 ID 全局递增，`inboxEvents(after)` 能从任意位置继续读，没有遗漏，也没有重复。
- `unreadSummary` 的数字和逐条读取时实际得到的未读数一致，并正确标出哪些时间线里有 @ 了自己的消息。

### 3.7 任务

- 一条消息上可以有多个任务；创建任务不会自动指派给任何人。
- 两个账号同时认领同一个任务，只有一个成功。
- 已经不是任务主人的人迟到的"让出"，不改变当前主人。
- 只有当前主人能转交任务，且不能转交给自己。
- 能读一个频道，不代表能操作它的任务：非成员不能认领或接收任务。
- 任务变化不产生聊天消息。

### 3.8 推送

- 只有 Agent 发给所有者的私信，或 @ 了所有者的消息，会进入推送队列；邮箱地址里的 `@owner` 这类写法不算提及。
- 推送服务返回暂时性失败时，按退避重试，重启后继续重试；返回 404/410 时删除该订阅，不再重试。
- 推送失败不影响消息本身。
- 推送内容不包含消息正文，同一条消息重复推送时使用相同的 tag。

### 3.9 实时事件流

- 快照和它对应的事件游标在同一次读取中得到：在两者之间提交的消息，不会既不在快照里、也不在后续事件里。
- 游标早于服务端保留的最早事件时，返回"需要重新拉快照"。
- 游标所属的纪元和服务端当前纪元不同时（数据被重置过），同样返回"需要重新拉快照"。
- 登录会话过期后，事件流发出"需要登录"并关闭，不再发送任何事件。

## 4. Agent runtime

**边界：** `AgentRuntime` 接口，加上它发给模型提供商的 HTTP 请求和发给网关、聊天 app 的调用。

**替身：** 脚本化提供商、故障存储适配器、可控时钟、假聊天 app（或真实聊天 app）、假 node（经由真实网关，或直接用网关替身）。

### 4.1 loop 与上下文

- 提交一条输入后，模型被调用；模型发起工具调用，工具结果交回模型，直到模型给出最终回答。
- 模型的最终文字不会被发到任何聊天会话。
- 同一个 Agent 先后多次输入，模型每次看到的都是同一个上下文的延续：请求体的前缀逐次只增不改，包括关闭再打开 runtime 之后。
- 两个 Agent 的上下文互不可见。
- 上下文超过模型窗口时会自动压缩，压缩之后 Agent 能继续工作，压缩前的记录仍能通过历史工具读到。
- 摘要请求失败或被截断时，不使用这个摘要，原上下文保持不变。
- 改了模型或 thinking 级别之后，下一次请求就使用新设置；正在进行的请求不受影响。

### 4.2 收件箱

- 同一个 `requestId` 提交两次，模型只看到一次。
- Agent 正在运行时，以 `steer` 提交的输入出现在当前这轮工具调用之后，不会另开一次 run。
- `withdraw` 一条还没交给模型的提交后，模型永远看不到它。

### 4.3 工具与崩溃

- 模型的工具调用参数还没有完整流完时就崩溃，重启后这个工具不会被执行。
- 有副作用、且没有声明可重做的工具（如 `bash`）在执行中崩溃，重启后不会重新执行，模型收到"已中断"。
- 聊天工具在执行中崩溃（聊天 app 已经发出消息，但工具结果还没提交），重启后重新执行，聊天 app 按 `requestId` 原样返回结果，频道里只有一条消息。
- `readUnread` 在同样的位置崩溃，重启后模型拿到的正是第一次读到的那一页。
- 工具调用的 `requestId` 来自 Durable 的工具调用 ID，而不是提供商的调用 ID：两次独立的工具调用即使提供商给了相同的调用 ID，也各自执行。
- 工作助手没有聊天工具：助手的工具列表里没有聊天工具；脚本化提供商让助手强行调用聊天工具名时，调用失败，聊天 app 没有收到任何调用。

### 4.4 关闭与重新打开

- `close()` 时正在进行的模型请求被中止：脚本化提供商观察到连接断开，迟到的回应不会产生任何效果。这一点要在请求的各个阶段都验证：发出前、等待响应头、流式传输中（文字和工具调用参数）、摘要请求中（随压缩一起在 M5 做）。
- `close()` 时正在进行的 node 工具调用被停止。
- 关闭后重新打开，未完成的工作从停下的地方继续，模型的上下文前缀不变。
- 存储提交失败时，runtime 不会挂起：这次工作以失败结束（等待它的调用不再挂住，而是报错），runtime 调用一次 `onFatal` 后就死了；它不会自己重开，由 Agent Manager 关闭它，之后重新打开的 runtime 从存储里的状态继续，并能接收、回答新的输入。

### 4.5 工作助手

- 派生助手的工具调用崩溃后重做，不会派生第二个助手。
- 助手完成后，向派生它的对话汇报恰好一次；汇报在崩溃后不会重复，也不会丢失。
- 中断一个助手不影响别的助手，也不影响主对话。
- 关闭 runtime 时，主对话和所有助手一起停止；重新打开后，各助手继续各自原来的上下文。

### 4.6 提醒

- 设定的提醒到时间后，作为一条输入提交给主对话。
- 提醒在 runtime 关闭期间到期时，重新打开后立即触发，并且只触发一次。
- 提醒触发后在提交之前崩溃，重启后只触发一次。

### 4.7 用量

- 每次模型请求后，`usage()` 的数字增加；脚本化提供商返回的 token 数如实反映在里面。
- 不存在任何会因为用量过高而停止 Agent 的行为。

## 5. 连接器

**边界：** 输入是聊天 app 的 `inboxEvents` 和 `unreadSummary`，输出是对 runtime 的 `submit` 和 `withdraw`。

**替身：** 测试连接器时，用真实聊天 app 加上一个记录 `submit` 和 `withdraw` 的假 runtime；验证与 Durable 的组合时，用真实 runtime 加故障存储适配器。

- 一条新收件事件产生一条通知，`requestId` 是 `notice:<事件 ID>`，`whenBusy` 是 `steer`。
- 通知文字写明时间点、"至少"多少条、各时间线的条数、是否 @ 了你，以及"之后可能还有更多"。
- 已有一条通知还没交给模型时，又来了新事件：旧通知被撤回，新通知反映最新状态，模型最终只看到新的那条。
- 撤回时旧通知恰好已经交给了模型：新通知仍然照常提交，模型先后看到两条。
- 提交通知之后、保存事件位置之前崩溃：重启后重新提交同一个 `requestId`，模型只看到一次。
- runtime 关闭期间来了很多事件：重新打开后只产生一条通知，数字反映全部未读。
- 只有任务条目变化、没有新消息时，不产生通知。

## 6. Agent Manager

**边界：** `AgentManager` 接口和 `data/agents/` 目录。

**替身：** 真实聊天 app、真实 runtime、假 node（经由真实网关）、脚本化提供商。

- 创建 Agent 后，聊天 app 里有对应账号，node 上有工作目录，`data/agents/` 里有它的文件。
- 创建流程在每一步之后中断，重做一遍都能得到完整的 Agent，不会出现两个聊天账号或两个文件。
- 文件改名之前中断：Manager 重启后看不到这个 Agent。
- 重启后，Manager 打开所有没有暂停的 Agent，跳过已暂停的。
- 对同一个 Agent 并发调用暂停、恢复、暂停，最终状态和这些调用按到达顺序依次执行的结果一致，并且任何时刻最多只有一个已打开的 runtime。
- 暂停后：模型请求被中止，node 上的工具调用被停止，之后发来的消息不会让模型被调用；恢复后，模型看到暂停期间累积的通知。
- 暂停状态在控制面重启后仍然保持。
- 删除 Agent 后，它的文件不存在，聊天账号被停用，它过去发的消息仍然可读。
- 一个 Agent 的存储文件损坏，其他 Agent 照常启动和工作。

## 7. Node 网关

**边界：** `NodeGateway` 接口，以及它对 node 说的 WebSocket 协议。

**替身：** 假 node、网络代理、可控时钟。

- 配对令牌只能用一次，过期后不能用；令牌只以哈希形式存储。
- 配对只新增 node：用有效令牌配对一个已配对的 node ID 被拒绝，原来的公钥照常认证，令牌没有被用掉。
- 已配对的 node 用签名认证；只有在控制面明确回答"不认识这个身份"之后，node 才会用配对令牌。
- 同一个 node 建立新连接后，旧连接被关闭，来自旧连接的消息一律被拒绝。
- `runTool` 把输出流式交给调用方，最后返回结果。
- 两个 Agent 在同一个 node 上并发调用，各自拿到自己的输出和结果：网关为每次调用生成自己的请求 ID。
- 调用没有自己的期限：时钟推进很久之后，node 送来的真实结果照常交给调用方。
- 调用方中止调用：网关立即以"已停止"（不是"结果未知"）结束它，并让 node 停掉这一次调用；之后 node 送来的输出和结果被丢弃。
- Agent ID 不合法的调用在发送和注册任何东西之前就被拒绝。
- 工具调用进行中连接断开：调用立即以"结果未知"结束；之后即使假 node 重连并送来这次调用的结果，也被丢弃，不会交给调用方。
- node 离线时调用 `runTool`，立即返回"节点离线"，不排队等待。
- 黑洞连接（TCP 没断但收不到数据，node 仍在发心跳）在心跳超时后被判定离线。
- 未认证的连接数量和消息大小（按序列化后的帧计）有上限；超限、格式错误或顺序错误（认证前发别的消息、重复认证）的连接被关闭，之后它送来的消息一律不读。
- 握手超时以协议错误（`gateway.error`）结束连接，不是身份拒绝。
- 一个 node 断开，不影响其他 node 上的调用。
- node 注册表存在 `control.sqlite` 里，和别的模块的表共处：别的模块的表在、版本不同，网关照常打开，重启后已配对的 node 照常认证，别的模块的数据不受影响，数据目录里除了 `control.sqlite` 没有别的文件；别的模块开着读事务时，网关照常配对 node。
- 网关自己的表版本不对，或者别的模块已经占了它的表名，网关拒绝启动，抛出的 `ControlStoreIncompatible` 带着 `control.sqlite` 的路径；别的模块照常打开。

## 8. Node

**边界：** node 进程对网关说的 WebSocket 协议，以及它在文件系统和进程上的实际效果。测试在真实 Linux 上运行（`pnpm test:linux` 在 Linux 容器里以非 root 账号运行，macOS 上只跑不依赖 Linux 的部分），以子进程启动 node。

**替身：** 假网关。

### 8.1 命令

- 命令原样交给 `/bin/sh -c` 执行，工作目录和 HOME 是该 Agent 的工作目录。
- Agent 自己写的 `sudo` 原样执行，成败由宿主决定；node 从不自己加 `sudo`。
- 返回的结果如实区分：正常退出（附退出码）、被信号终止、超时被杀、没能启动（例如工作目录不存在）。
- 输出超过上限时截断，并在结果里标明。
- `timeout` 超过协议规定的上限时，命令不执行，返回参数错误。
- 命令退出后，后台子进程仍占着输出管道：node 不会一直等下去，在短暂等待后返回，并标明输出可能不完整。
- 进程组里只剩僵尸进程时，算作已经结束。
- 记录下来的 PID 被系统复用给别的进程后，停止操作不会误杀那个进程。

### 8.2 文件

- 文件工具（`read`、`write`、`edit`）的行为与 Durable 自带工具在本地执行时一致。
- 以两个点开头的普通文件名（`..notes.md`、`...`、`..cache/x.txt`）照常读写。
- 路径不能逃出工作目录：`..`、指向工作目录外的绝对路径、指向外部的符号链接都被拒绝。（Durable 的文件工具内部会把路径先变成绝对路径再解析，所以指向工作目录内的绝对路径照常可用。）
- 读取时文件被别人修改，返回"文件已改变"，而不是拼接出新旧混合的内容。

### 8.3 连接与停止

- 连接断开时，正在运行的、由工具调用启动的进程组被停止。
- 网关停止一次调用，只杀掉这次调用的进程组，同一个 Agent 和其他 Agent 的其他调用照常运行。
- 命令已经返回、后台进程还占着输出时收到停止，后台进程也被杀掉。
- 通过真实网关：调用方中止调用后，node 上这次调用的进程组消失，调用方得到"已停止"；另一个 Agent 的并发调用不受影响，拿到自己的结果。
- node 自己关闭时，停止所有它启动的进程组，包括命令已经返回、但还留着后台进程组的那些。
- 修改或删除工作目录里的 `MEMORY.md`，不影响之后的命令执行。
- 工作目录不存在时，工具调用以明确的错误失败，node 不会自己重建它。
- 身份被拒绝时，node 退出，不会无限重试；网络失败或网关以协议错误（例如握手超时）结束连接时，按退避重连。

## 9. Node 管理 CLI

**边界：** `mate node` 命令行。

**替身：** 假 systemd，加上临时目录作为 HOME。

- `install` 首次安装后，服务被启用并启动；重复执行 `install`，不会重启或重新启用一个被所有者手动停止或禁用的服务。
- `update` 在服务没有完全停止时拒绝执行，并且不做任何改动。
- `update` 在每一步之后中断，重新执行同一个命令都能完成更新。
- `uninstall` 保留配置、身份、工作区和数据；在每一步之后中断，重新执行都能完成卸载。
- 从不删除不属于 Mate 的文件：安装目录里多出来的文件被保留，并在输出里报告。
- 以 root 运行时拒绝执行。
- 下载凭据只传给下载程序，不出现在其他子进程的环境变量里。
- 发布包的校验和不匹配、包里有链接或多余文件时，拒绝安装，并且不改动已安装的任何东西。

## 10. 管理模块

**边界：** 管理模块的接口，以及它的 HTTP 路由（经 Web 外壳）。

**替身：** 真实 Manager 和 runtime、假 node、脚本化提供商。

- 设置模型时，只接受该提供商已经配置了 API key 的模型；不支持的 thinking 级别直接被拒绝，不会被悄悄降级。
- 修改 API key 后，下一次模型请求使用新 key；用同样的值再保存一次，不会打断正在运行的 Agent。
- 查看对话记录时，能实时看到流式输出和工具调用；查看不会改变 Agent 的任何状态。
- 浏览工作区是只读的，路径不能逃出该 Agent 的工作目录。
- 配对 node：生成的令牌只能用一次。

## 11. Web 外壳

**边界：** HTTP 接口，加上浏览器里的页面行为。页面测试用浏览器测试工具（如 Playwright），驱动真实的前端和后端，后端的模型用脚本化提供商。

### 11.1 后端

- 未登录访问 API 返回 401，访问页面跳转到登录页，并带上原本要去的地址。
- 登录后的跳转只接受站内 `/app` 路径。
- 连续输错密码不会把所有者锁在外面；同时进行的密码校验数量有上限，超出时返回 429。
- 初始密码文件只在第一次启动时读取。
- 会话令牌只以哈希形式存储；退出登录后这个令牌立即失效。

### 11.2 前端

- 打开页面时选中的频道，在事件流建立之前就已确定：建立事件流时立即到达的消息不会丢失。
- 重放或重复的事件不会产生重复消息，也不会让讨论串的回复数虚增。
- 切换频道后，旧频道迟到的响应不会覆盖新频道的内容。
- 消息发送过程中又输入的文字，在发送成功后仍然保留。
- 发送请求的响应丢失后重试，不会产生重复消息（同一个请求 ID）。
- 收到"需要重新拉快照"后，页面重新加载状态，而不是停住。
- 会话过期时跳转到登录页，登录后回到原来的位置。
- 从推送通知点进来，直接定位到那条消息；消息不存在时，退回到最新消息，并显示提示。
- 手机宽度下可用。

## 12. 系统场景

少量端到端测试，把整个系统当作一个模块：以真实子进程启动控制面和 node，模型用脚本化提供商，所有者的操作通过 HTTP 发出。它们证明各模块确实接在了一起；具体的边界情况应当在各模块的测试里覆盖，而不是在这里。

1. 所有者在频道里 @ 一个 Agent，Agent 读取后回复。
2. Agent 运行一条长命令期间，所有者又发了两条消息：Agent 收到一条通知，读到两条消息，完成命令后回复。
3. Agent 读完频道后、发言前，所有者又发了一条：Agent 的发言被拦下，它重新组织内容后再发。
4. Agent 执行命令期间控制面被 SIGKILL，然后重启：这条命令不会被再次执行，Agent 收到"已中断"，并继续工作。
5. Agent 执行命令期间 node 网络断开：Agent 收到"结果未知"，继续读写消息；node 恢复后，新的命令正常执行。
6. 所有者暂停一个正在运行的 Agent，再恢复：暂停期间模型没有被调用，恢复后 Agent 处理积压的通知。
7. 两个 Agent 在私信里协作：A 派一个任务给 B，B 认领并完成，A 收到通知。
8. Agent 派生一个工作助手执行命令，助手完成后汇报，Agent 把结果发到频道。
