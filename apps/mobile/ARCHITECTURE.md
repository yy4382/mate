# 移动客户端（`@palace/mobile`）

> 总览见 [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md)。开发、构建和 TestFlight 发布见 [DEPLOYMENT §6.1–6.2](../../docs/DEPLOYMENT.md)。测试见 [TESTS.md](TESTS.md)。

## 范围

自用的 iOS 27+ 客户端，用 Expo 和 Expo Router。覆盖服务器选择、cookie 登录与恢复、频道和私信、讨论串、搜索、提及、任务、未读、完整管理、Agent 观察、个人资料和原生通知。聊天和管理复用控制面现有的 HTTP 路由和 SSE 协议，类型来自 `@palace/chat/contracts`、`@palace/admin` 和 `@palace/control-plane/contracts`，在网络边界用 schema 解析响应，不复制服务端协议。服务端仍负责每次请求的角色检查。

## 一次登录拥有的对象

`lifecycle.ts` 的 `startMobileLifecycle` 是唯一订阅认证状态和 AppState 的地方。只有已登录且在前台时会话才可用。它据此设置通知会话、暂停或恢复聊天流，并在界面显示的身份变化时创建或关闭这次登录的 `MobileChat`。

每次登录有：

- 一个 `MobileChat`：持有聊天数据、草稿、未完成的发送和未确认的操作输入。
- 一个 `ManagementScope`：位于所有已登录 Tab 之上，含一个 `ManagementClient` 和一个 QueryClient，切换 Tab 不另建。
- 通知会话：由生命周期设置，后台的身份更新不能恢复通知访问。

登录结束、401 确认失效，或服务器、账号、角色改变时，这些对象随旧登录一起关闭，新登录从空状态开始，所以迟到的旧回调写不到新登录的状态里。草稿只在内存里，不跨 app 重启。

## 认证

`MobileAuth` 持有认证，`auth-native.ts` 接入系统 `fetch`、Foundation cookie 清理和 Expo SQLite 键值设置。

- **保存的东西。** 服务器地址、是否允许恢复登录的标记，以及允许恢复时最近一次 `/api/me` 验证的身份。不保存密码。cookie 由原生网络栈保存，正常使用后可跨启动恢复。
- **验证前不碰聊天数据。** 冷启动用保存的身份直接显示 app，但 `MobileChat` 和 `ManagementClient` 在验证通过前处于暂停状态，所有请求等待，下拉刷新和重试也不打破暂停。验证出另一个账号时，旧实例直接关闭。
- **重验。** 只有真正进入 background 再回到 active 才重验，权限弹窗造成的 inactive 到 active 不重验。重验期间保留当前导航、草稿和缓存，危险操作和选择器隐藏。401 要求重新登录；网络或服务器故障遮挡界面、保留恢复资格并提供重试。
- **退出与换服务器。** 先保存禁止恢复的标记，再尝试 `POST /api/logout`，无论远端是否可达都清理本机 cookie，远端撤销未确认时明确提示。换服务器时没有会话就不联系旧服务器。登录请求不重叠，退出和换服务器使旧请求的响应失效。`beforeClear` 屏障等取消通知登记结束后才清理 cookie。
- **服务器地址只在 `MobileAuth` 的解析入口校验**，要求 HTTPS、非空主机、无凭据、根路径、无查询和片段，返回规范 origin。界面不另做字符串修补。

## 聊天

- **发送和操作可以安全重试。** 请求 ID 由 Expo Crypto 生成，响应丢失后重试沿用同一个 ID。频道创建、成员操作和任务操作的未确认输入和 ID 由 `MobileChat` 持有，关闭界面再打开也不丢；收到确认或明确拒绝后才清除。未确认期间只重试原操作，不用另一份输入产生重复创建。
- **快照先于事件流。** 快照建立游标后，历史、定位和发送即可用，不等事件流的第一个数据块。历史加载期间到达的实时条目按序号合并。会话列表的顺序、预览和时间只由快照的 `activity` 和之后的顶层条目事件推出，讨论串事件不改它。
- **事件流。** 用 `expo/fetch` 流式读取，`eventsource-parser` 分帧，凭据来自与认证相同的 cookie 存储。断线带最后应用的游标重连，40 秒没有数据或心跳就重连。`resnapshot` 重新拉数据并保留草稿。后台不推进已读位置。
- **定位一次就完成。** `/conversation?id=&thread=&seq=` 经历史分页加载目标，等列表实际测量后才确认定位。定位完成、失败或目标不可用之后，焦点变化、重验和重连都不重新定位，只有显式重试、换目标或时间线重新加载才重新开始。

## 管理

`ManagementClient` 只给这次登录的服务器和人类发 cookie 请求。重验时中止旧请求，已取消请求的迟到响应在恢复后也不交付。HTTP 401 和 SSE 的 `login` 都交给认证模块重验。

创建 Agent 的草稿属于这次登录的 `ManagementScope`，连同请求前生成的 Agent ID。返回、关闭管理或重验都保留它，继续创建时原样提交这个 ID；上一次请求已在服务器完成时，从 Agent 列表确认同一个 ID。添加人类同样在结果未确认时保留输入和 `requestId`，只重试原操作。

React Native 隐藏 modal 时会卸载它的子树，所以短表单和转交等展示草稿由 modal 外的页面持有。

观察和工作区浏览复用网页的接口，只读，不新增写文件或下载能力。

## 原生通知

`MobileNotifications`（`notifications.ts`）持有系统权限、已验证的服务器与账号、本机登记和未确认的取消登记。`notifications-native.ts` 用 `expo-notifications` 取得 APNs token、监听 token 更新、接收通知和点击。

- **只有订阅应答成功才算已登记。** 权限、环境和网络任一不满足都显示未完成，不猜。认证和通知只发布结构化事实，由界面翻译。
- **binding 把通知绑到一次登记。** 每次登记有随机 binding，同一 token 的重试沿用它，token 轮换生成新的。点击的通知必须带当前登记的 binding 且不超过一天，所以旧通知不会在另一个账号或服务器下打开。点击只产生站内的 `/conversation` 参数，忽略 payload 里的 URL。冷启动的点击等身份验证完成。
- **取消登记不会丢。** 当前登记和待取消登记分开保存。token 轮换前先持久化旧登记的取消记录，再发新登记。每条待取消记录带精确的服务器、账号、token、环境和 binding，只能用同一服务器和账号的已验证身份发送，刷新、重启恢复和退出时都会重试，服务端确认后才删除。
- **离线取消做不到的事要说清楚。** 离线时无法让服务器立即停止发送，也收不回已交给 APNs 的通知。本机立即禁止旧通知导航并向系统取消注册，界面说明取消未确认。

## 本地化

入口 `index.ts` 在加载路由前同步读设备语言偏好：zh 变体用简体中文，en 变体用英文，否则英文。i18next 资源随构建打包，Hermes 缺少的 `Intl` 部分由 FormatJS 补上，只带中英文数据。系统改语言后重启 app 生效，没有应用内语言选择。用户和 Agent 的内容、协议值和通知 payload 保持原文，系统通知文案由 iOS 按 `loc-key` 显示。

## 包的边界

`@palace/mobile` 自己持有依赖和 TypeScript 配置，不继承服务端的 NodeNext 配置，也不改网页的 React 版本。它没有 `build` 脚本，所以根 `build`、控制面构建和 node 发布包都不需要 Xcode 或签名凭据。
